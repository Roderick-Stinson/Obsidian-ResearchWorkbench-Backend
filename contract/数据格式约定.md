# 论文工作台 · 前后端接口约定（v2）

本文件规定论文面板（Obsidian + Dataview，见 `面板组件/view.js`）与后端服务之间的接口。前后端都按这里实现，有出入时以本文件和 `schemas/` 为准。

- `schemas/`：每种请求体和返回体的 JSON Schema（draft 2020-12）。
- `examples/`：每种返回体和请求体的示例。示例内容取自现有快照和 `view.js` 的演示数据，**不是真实结果**。
- `validate.py`：校验脚本，`python validate.py <文件或目录>...`（依赖 `pip install jsonschema`）。后端可以在测试里用它检查自己的输出。

> 状态：v2 已按 2026-10-28 的评审意见重写；后端骨架（`~/PaperWorkbench`）和面板都已按此实现，流水线尚未实现。v1 是"后端把文件写进 vault"的方案，已废弃。

## 1. 总体结构

```
┌──────── 后端服务（本机，以后可迁到服务器）────────┐            ┌──── Obsidian vault（只负责展示）────┐
│ 论文库：元数据、各版本、PDF、全文、分析结果          │            │ 面板代码 view.js / view.css          │
│ 你的数据：评分、标记、关注、阅读队列、研究兴趣       │  HTTP/JSON │ 面板配置 config.json（后端地址）     │
│ 每日流水线、LLM 分析、外部数据源、Telegram 推送      │ ◀────────▶ │ 阅读笔记（论文阅读/）                │
│ GPU 服务器上的实验守护进程把运行记录报给它           │            │ 实验记录、我的论文（你自己写的）      │
└──────────────────────────────────────────────────┘            └──────────────────────────────────────┘
```

两条原则：

1. **后端的数据都不放进 vault。** 论文条目、PDF、分析结果、你的评分和标记都存在后端。迁移服务器时只需搬后端，再改面板里的地址。
2. **后端从不读写 vault。** vault 里只有前端会写：阅读笔记和面板配置。本人论文和其他论文一样存在后端论文库里；vault 里 `我的论文/` 下是你对自己工作的思考笔记，后端不读。

## 2. 连接与通用规则

### 2.1 后端地址

面板从 `面板组件/config.json` 读取连接配置：

```json
{ "apiBase": "http://127.0.0.1:8765/api/v1", "token": "" }
```

- 本机运行时 `token` 留空，后端只监听 `127.0.0.1`。
- 迁到服务器后必须设置 `token`，并且走 HTTPS。前端在每个请求上带 `Authorization: Bearer <token>`。注意 vault 通过 Dropbox 同步，token 会随之同步到你的其他设备。
- 前端用 Obsidian 的 `requestUrl` 发请求（不受浏览器跨域限制）。

### 2.2 格式

- 请求体和返回体都是 UTF-8 JSON；PDF 下载除外。
- 所有返回体顶层都带 `kind`（返回体类型，与 schema 文件名一致）和 `schemaVersion`（当前为 `1`）。
- 由流水线生成的数据（简报、推荐、发展史等）还带 `generatedAt`，可选带 `runId`（产生它的流水线运行 ID）。
- 读取方必须忽略不认识的字段。新增可选字段不升版本；删除、改名、改类型或改含义时 `schemaVersion` 加 1。

### 2.3 错误

非 2xx 状态码时，返回体为：

```json
{ "kind": "error", "schemaVersion": 1, "error": { "code": "not_found", "message": "论文不存在：arxiv-2610.99999" } }
```

| 状态码 | `code` | 含义 |
|---|---|---|
| 400 | `invalid_params` | 参数或请求体不合法 |
| 401 | `unauthorized` | token 缺失或错误 |
| 404 | `not_found` | 资源不存在，或这项数据还没生成过 |
| 409 | `conflict` | 与当前状态冲突，例如重复提交同一个任务 |
| 503 | `unavailable` | 后端暂时不能处理，例如正在迁移数据 |
| 500 | `internal` | 后端内部错误（bug），详情看后端日志 |

**"还没生成"和"生成了但为空"要区分开：** 还没生成过返回 404；生成过但没有内容，返回 200 和空数组。

### 2.4 时间

- 时间点用带时区的 ISO 8601，例如 `2026-10-27T15:39:49+08:00`。
- 只表示日期时用 `YYYY-MM-DD`，按北京时间（Asia/Shanghai）切日。
- 时间段用 `{"start": "YYYY-MM-DD", "end": "YYYY-MM-DD"}`，两端都包含。

### 2.5 分页

列表接口接受 `?limit=`（默认 50，最大 200）和 `?cursor=`，返回 `{items, nextCursor, total}`。`nextCursor` 为 `null` 表示没有下一页。

### 2.6 离线

后端连不上时，前端显示上一次成功拉取的数据，并标明"离线 · 上次同步于 ……"。缓存放在 Obsidian 的本地存储里，不写进 vault。

### 2.7 文本

字符串字段都是纯文本。只有名为 `markdown` 的字段是 Markdown，前端用 Obsidian 的 Markdown 渲染器显示。由 LLM 生成的结论必须带出处（`sources` 或 `evidence`），没有出处就不要输出。

## 3. 论文 ID

### 3.1 格式

`<来源>-<来源内编号>`，正则 `^[a-z][a-z0-9]*-[A-Za-z0-9._-]+$`。

| 来源 | 示例 |
|---|---|
| arXiv | `arxiv-2610.32060`（不带版本号） |
| OpenReview | `openreview-imcyVlzpXh` |
| AAAI | `aaai-39481` |
| ACL Anthology | `acl-2025.acl-long.123` |
| PMLR（ICML 等） | `pmlr-v235-zhang24a` |
| NeurIPS 论文集 | `neurips-2025-<论文集里的 hash>` |
| 期刊 DOI | `doi-10.1109_tpami.2026.1234567`（`/` 换成 `_`） |

### 3.2 中稿后换成正式 ID

主 ID 取这篇论文**目前最正式的版本**，优先级：

1. 正式出版版本（camera-ready）：期刊 DOI、ACL Anthology、AAAI、PMLR、NeurIPS 论文集等；
2. OpenReview；
3. arXiv。

- 后端定期检查已收录论文有没有出现更正式的版本（流水线步骤 `version-check`），有就把主 ID 换过去。
- 旧 ID 进入 `aliases`，**永久保留**。所有接受论文 ID 的接口都接受别名，返回体里的 `id` 一律是当前主 ID。
- 你的评分、标记、关注、阅读队列、研究兴趣证据，在后端里随主 ID 一起迁移。
- ICLR、NeurIPS、ICML 在 OpenReview 上审稿，中稿后 forum id 不变。所以实际会换 ID 的，主要是 arXiv 预印本中稿的情况，以及会议论文集出版之后。

### 3.3 阅读笔记里的 ID

阅读笔记留在 vault 里，用 frontmatter 的 `paper_id` 关联论文。笔记由你维护，后端不会去改它。前端打开面板时把笔记里的 ID 交给 `POST /papers/resolve`，发现 ID 已变化时，由前端把笔记里的 `paper_id` 改成新 ID。

### 3.4 论文引用（PaperRef）

凡是"指向一篇论文"的地方都用同一个对象：

```json
{ "id": "arxiv-2610.32060", "title": "论文标题", "url": "https://arxiv.org/abs/2610.32060" }
```

`url` 可选，指向外部原文。论文不在论文库里时（例如经典工作的原论文还没收录），`id` 为 `null`，但 `title` 必填。

## 5. 各接口的数据

字段表里的"现有字段"指 `view.js` 演示数据里的对应字段，方便改前端。

### 5.1 `overview`

每次请求时直接从论文库计算，不依赖流水线。`relevantTotal` 是领域检索判定为核心相关或相关的篇数。

| 字段 | 类型 | 说明 |
|---|---|---|
| `paperTotal` | 整数 | 论文库总数 |
| `relevantTotal` | 整数 | 与你的研究兴趣相关的篇数 |
| `newLast7Days` | 整数 | 近 7 天新收录 |
| `lastIngestAt` | 时间 / null | 最近一次成功抓取 |

阅读进度（已读笔记数）由前端根据 vault 里的阅读笔记计算，不经过后端。

### 5.2 `pipeline`

| 字段 | 类型 | 说明 |
|---|---|---|
| `schedule[]` | 数组 | 系统日程 `{when, what, panel}`，替代 `MANUAL` |
| `latestRun` | 对象 / null | 最近一次每日流水线：`{runId, date, status, startedAt, finishedAt, steps[]}` |
| `latestRun.steps[]` | 数组 | `{key, name, status, startedAt, finishedAt, attempts, error}`，替代 `STEPS` |
| `attention[]` | 数组 | 需要你看的事项：`{id, source, severity, title, summary, since, link}` |

- `latestRun.status`：`running` / `ok` / `partial`（有步骤失败）/ `failed`。
- `steps[].status`：`pending` / `running` / `ok` / `failed` / `skipped`。
- `attention[].source`：`pipeline` / `experiment` / `ingest` / `task`；`severity`：`info` / `warn` / `error`。

步骤 `key` 固定为：

| key | 名称 |
|---|---|
| `fetch` | 抓取新论文 |
| `version-check` | 检查中稿，升级论文 ID |
| `classify` | 按研究兴趣判定相关性 |
| `skim` | 读全文速读 |
| `recommend` | 分出核心 / 邻近 / 热点三类推荐 |
| `pick` | 挑选精选（≤10 篇） |
| `deep-read` | 写精读 |
| `results` | 更新结果表 |
| `map` | 领域地图重组 |
| `must-read` | 更新必读 |
| `classics` | 更新经典 |
| `interests` | 更新候选关键词 |
| `research-lines` | 推进研究线 |
| `hotspots` | 整理热点 |
| `report` | 生成报告 |
| `push` | 推送 Telegram |

### 5.3 `brief`

不带 `date` 时返回最新一期。

| 字段 | 类型 | 说明 | 现有字段 |
|---|---|---|---|
| `date` | 日期 | 这期简报对应的日期 | `brief.date` |
| `updatedAt` | 时间 | 最后一次补充更新 | `brief.updatedAt` |
| `newCount` / `pickedCount` | 整数 | 当日新收录 / 精选篇数 | 同名 |
| `summary` | 字符串 | 一段话总结 | `brief.summary` |
| `highlights[]` | 数组 | `{title, text, sources: PaperRef[]}` | `brief.highlights` |
| `picks[]` | 数组 | BriefPaper，加 `reason`（入选理由），最多 10 篇 | `brief.picks` |
| `todayNew[]` | 数组 | BriefPaper | 顶层 `todayNew` |
| `weekly` | 对象 / null | `{period, summary, reportId}` | `weeklySummary` + `weeklyPeriod` |

BriefPaper：`{id, title, summary, publishedAt, url}`。

### 5.4 推荐：`recommendations-index`、`recommendations-day`

每天的推荐分三类，**不设比例和数量上限，找到多少就是多少**：

| `category` | 名称 | 含义 |
|---|---|---|
| `core` | 核心 | 与你的关键词树直接匹配 |
| `adjacent` | 邻近 | 和你标为相关的论文有引用关系，但不在你的关键词里 |
| `trending` | 热点 | 在你设定的一级领域里增长快、讨论多，不看关键词 |

`recommendations-index`：`issues[]`，每项 `{date, counts: {core, adjacent, trending}, pickedCount}`，按日期倒序，保留最近 90 天。

`recommendations-day`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `date` | 日期 | |
| `counts` | 对象 | `{core, adjacent, trending}`，与 `papers` 中各类篇数一致 |
| `papers[]` | 数组 | Recommendation，先按 `core` → `adjacent` → `trending` 分组，组内按 `score` 从高到低 |

Recommendation：

| 字段 | 类型 | 说明 | 现有字段 |
|---|---|---|---|
| `id` | 论文 ID | | `id`（需加来源前缀） |
| `titleZh` / `titleEn` | 字符串 | 中文结论式标题 / 原文标题 | `zh` / `en` |
| `summary` | 字符串 | 速读摘要 | `sum` |
| `publishedAt` | 日期 | | `date` |
| `url` | 字符串 | 原文链接 | — |
| `codeUrl` | 字符串 / null | | `code`（布尔） |
| `hfUpvotes` | 整数 | Hugging Face Papers 点赞数，未上榜填 0 | `hf` |
| `citations` | 对象 | `{count, updatedAt}`，`count` 拿不到时为 null | 替代 `seeds` |
| `quality` | 对象 | `{score, rationale}`，`score` 为 0–10 | `q` |
| `category` | 枚举 | `core` / `adjacent` / `trending` | — |
| `reason` | 字符串 | 为什么推荐，例如"引用了你标为相关的 MaAS" | — |
| `matchedKeywords[]` | 数组 | `{nodeId, label}`，命中的关键词；`trending` 可以为空 | 替代 `obj` / `search` / `gran` / `type` |
| `score` | 数字 | 0–1，组内排序依据 | — |
| `picked` | 布尔 | 是否入选当日精选 | — |
| `user` | 对象 | 你对这篇的标记，见 5.6 的 `paper-user` | `S.ratings` / `S.flags` |

新出的论文被引量通常是 0，所以 `citations` 主要对稍早的论文有区分度。

偏好设置里原有的"每日推荐数量"不再需要，已去掉。"只推荐有开源代码的论文"保留。

### 5.5 论文：`paper-list`、`paper`

论文条目和 PDF 只存在后端，不再放进 vault。

`paper-list`：`{items: PaperSummary[], nextCursor, total, facets}`。查询参数：

| 参数 | 说明 |
|---|---|
| `q` | 搜标题、中文标题、作者、会议、ID、一句话总结、摘要；空格分开的多个词须全部命中 |
| `watched` / `own` | `true` 只看重点关注 / 本人论文 |
| `topic` / `venue` / `year` / `status` / `relevance` | 分面筛选：方向、会议（不带年份，如 `ICML`）、年份、发表状态、相关程度（`core` / `related` / `none`） |
| `rating` | `unrated` 只看未评分；`1`–`5` 只看评分不低于它的 |
| `sort` | `relevance`（核心相关优先，再按被引）/ `newest` / `citations` / `rating` / `added`（默认，最近加入） |
| `facets` | `true` 时返回 `facets`：`{topic, venue, year, status, relevance}`，每项是 `[{label, count}]`；每个分面按“除它自己以外的筛选条件”计数 |`/papers/topics` 返回论文库里出现过的方向及篇数：`{items: [{label, count}]}`。

添加论文：`POST /papers`，请求体 `{title, url, own, watched}`（都可选，但 `title` 和 `url` 至少给一个，否则 400）。已有论文的标题还是 ID（收录时没拿到标题）时，用请求里的 `title` 补上。`url` 是 OpenReview 或 arXiv 链接时按链接定 ID（如 `openreview-AbCdEf1234`），否则生成 `local-<8 位十六进制>`。已在论文库里的不重复建，只把 `own` / `watched` 标记加上，返回 200；新建返回 201。

给了 arXiv / OpenReview 链接的论文，后端在后台补全信息、下载 PDF，不在请求里等，前端过一会儿重新读取即可：arXiv 论文从 arXiv 补上作者、年份、摘要，没填标题的也补上标题（你填过或改过的字段不动）；PDF 按“批量下载 PDF”同样的公开来源下载，OpenReview 论文按标题到 arXiv 找同名论文。下不到的在论文上显示“缺 PDF”，可以手动上传。已在论文库里但还没有 PDF 的，再添加一次也会重新尝试下载。

修正信息：`PATCH /papers/{id}`，请求体 `{title, titleZh, venue, year, firstAuthor, publicationStatus}` 中的任意几项。改过的字段名记进 `paper.userEdited`；领域检索重新入库、DBLP 核实等自动流程不再覆盖这些字段（发表状态是你手动设的论文不再自动核实）。论文的 `title` 还等于它的 ID 时，表示标题未知，前端应显示“未知标题”和原文链接，而不是直接显示 ID。

上传 PDF：`PUT /papers/{id}/pdf`，请求体就是 PDF 文件内容（不超过 100 MB，必须以 `%PDF` 开头），已有的会被替换。论文标题还未知时，后端从 PDF 第一页读出标题补上。返回更新后的 `paper`。

PaperSummary：`{id, title, titleZh, firstAuthor, year, venue, publicationStatus, hasPdf, citations, summary, urls, topics, libraryRelevance, user}`。

通过领域检索入库的论文另有三个字段（`paper` 里可选）：`topics`（判定所属的方向，取自关键词树的一二级和可解释性四个方向）、`libraryRelevance`（`core` 核心相关 / `related` 相关）、`libraryReason`（判定理由）、`abstract`（英文摘要）。其他论文 `topics` 为空数组、`libraryRelevance` 为 null。

### 5.7 研究兴趣：`interests`

关键词树由两部分组成：

1. **你填写的**（`origin: user`）：任何一级都可以自己添加、改名、写说明、删除。不需要证据，重新整理时永远保留。
2. **整理所得的**（`origin: extracted`）：后端根据论文库里**你重点关注的论文**、**本人论文**和**你标为"相关"的论文**的原文整理出来（vault 里的笔记不参与），每个关键词都附原文证据。重新整理时这部分整体替换。

另外：

- 你改过名字或说明的整理所得关键词，会转为你填写的，之后不再被替换。
- 你**固定**（pin）的关键词，重新整理时保留。
- 你**删除**的整理所得关键词，后端会记住，以后重新整理不再加回来。
- 每周流水线把一级领域里增长快的新方向作为**候选关键词**给你，你采纳后才加入树中（`origin: candidate`，重新整理时保留）。
- 推荐按整棵树打分，两部分一视同仁。

`interests`（还没有任何关键词时返回 404）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `generatedAt` | 时间 | 关键词树最近一次整理时间 |
| `overview` | 字符串 | 研究概述 |
| `basis` | 对象 | `{ownPapers, watchedPapers, relevantPapers}`，整理时用到的本人论文、关注论文、相关论文的数量 |
| `stale` | 布尔 | 这些论文有变化，还没重新整理 |
| `domains[]` | 数组 | 一级关键词节点 |
| `candidates[]` | 数组 | 候选关键词 |

关键词节点：`{id, label, summary, origin, pinned, evidence[], children[]}`

- 一级的 `children` 是二级，二级的 `children` 是三级，三级没有 `children`。`children` 可以为空。
- `origin`：`user` / `extracted` / `candidate`，含义见上。
- `evidence[]`：`{kind, ref, title, quote}`。`kind` 目前只有 `paper`，`ref` 是论文 ID；`quote` 为原文摘录，可为 null。`extracted` 和 `candidate` 节点至少一条证据，`user` 节点可以没有。
- 同一级的 `label` 不重复（不区分大小写），全树不超过 300 个节点。

修改关键词树：

- 添加：`POST /me/interests/nodes/{parentId}/children`，请求体 `{label, summary}`（`summary` 可选）。`parentId` 为 `root` 时添加一级。
- 改名或改说明：`PATCH /me/interests/nodes/{nodeId}`，请求体 `{label}`、`{summary}` 或两者都有。
- 固定、取消固定、删除：`POST /me/interests/nodes/{nodeId}/pin|unpin|remove`，任何一级都可以。删除会连同下级一起删除。

整理结果的格式是 `interests-extraction`：`{overview, basis, domains}`，`domains` 是不带 `id` / `origin` / `pinned` 的三级树，每个节点都有 `summary` 和至少一条证据。后端合并前会核对每条论文证据的 `quote` 确实出现在该论文的 PDF 原文里，有一条对不上就整体拒绝。合并时按名称与现有同级节点对齐：同名的你填写的节点保留不动，只在它下面并入整理所得的下级。

候选关键词：`{id, parentId, level, label, reason, growth: {paperCount, windowDays, changePct}, examples: PaperRef[]}`，`level` 为 2 或 3。

### 5.8 `deep-read`（AI 精读）

`{paperId, generatedAt, markdown, sources}`。由任务 `deep-read` 生成，存在后端，面板里直接显示。面板提供"存为阅读笔记"按钮，由**前端**在 `论文阅读/` 下创建笔记，并在 frontmatter 写入 `paper_id`。

### 5.9 `classics`

经典工作：被论文库里很多篇论文引用的工作（不限年份，2023 年以前的奠基工作也在内）。后端用 Semantic Scholar 取论文库每篇的参考文献，统计库内被引次数，再由大模型按技术路线分组、标角色、写理由。必读论文：论文库里核心相关的论文，按发表年份分三段（今年的新作、去年、更早），每段把全部核心相关论文交给大模型逐篇判断是否必读（标准：必须了解的问题设定或开创性工作、常用对比基线、某条技术路线的成熟或最新做法、会用到的评测集或重要发现），符合的都选，不限篇数；新作还没来得及被引用，不和老论文比被引，今年的新作也包括会议还没核实的 arXiv 论文（`venue` 后注明“中稿待核实”）。由任务 `rebuild-classics` 生成。

| 字段 | 类型 | 说明 |
|---|---|---|
| `rules` | 对象 | `{libraryCitationMin, libraryPapers, mustReadCount}`：入选经典要求的库内被引篇数、统计时论文库的篇数、必读篇数 |
| `factsUpdatedAt` | 时间 | 被引数等外部数据的抓取时间 |
| `startHere[]` | 数组 | `{paper, date, venue, why}`，建议的入门阅读顺序 |
| `routes[]` | 数组 | `{key, name, intro, items: [{paper, date, venue, role, why, evidence}]}`；路线取自关键词树的一二级和可解释性四个方向，另有“通用基础（大模型与通用方法）” |
| `mustRead[]` | 数组 | `{paper, date, period, venue, venueTier, why, evidence}`；`period` 是所在的年份分段，如“2026 年新作”（旧数据可能没有） |

- `date` 用 `YYYY-MM`，查不到月份时只写 `YYYY`。`role`：`开创` / `奠基` / `代表`。`venueTier`：`CCF-A 会议` / `CCF-A 期刊` / `其他`（ICLR、EMNLP、NAACL、Nature 子刊等归“其他”）。
- `evidence`：`{libraryCitations, citations, baselineCount, githubStars, codeUrl}`。`libraryCitations` 是论文库里引用它的篇数。`baselineCount`（被当作对比方法的次数）和 `githubStars` 目前没有数据，为 `null`；拿不到的数字都填 `null`，前端显示“—”。
- 经典工作不在论文库里时，`paper.id` 为 `null`，`paper.url` 指向 arXiv / DOI / Semantic Scholar。
- `routes[].key` 与 `map.json` 的 `categories[].routeKey` 共用一套取值。

### 5.10 `map`（领域发展史）

由任务 `rebuild-map` 生成（还没有经典与必读时会先生成它）。`trends` 和 `categories` 直接按论文库数据算；评测集由大模型列出名字、后端按论文标题和摘要实际计数（`usedByCount`），基线取库内被引最多的经典方法；`stages`、`gaps`、`intro` 由大模型写，里程碑和出处只能引用经典工作、论文库里的真实论文或全领域热点的代表论文。

论文库只收已中稿、和关键词树相关的论文，会滞后半年到一年，也看不到关键词树以外的新方向，所以另有 `hotspots`（全领域热点演变）：后端按月取 arXiv 上所有标题或摘要含 agent 的计算机类论文（`pwb feed`），统计每个词组每月出现在多少比例的论文里，挑出比例涨了很多的词组，由大模型归成热点（只能用数据里的词组），再按归好的词组逐月重新计数；起势月份 = 三个月平均占比从基线（最早四分之一时间段里的最低值）涨到峰值四分之一的月份。最近一年半的发展阶段以热点的起势先后为主线。

| 字段 | 类型 | 说明 | 现有字段 |
|---|---|---|---|
| `intro` | 字符串 | 领域总述 | `MAP.intro` |
| `stages[]` | 数组 | `{period, title, description, milestones: [{date, venue, paper, text}]}` | `MAP.stages` |
| `trends[]` | 数组 | `{direction, trend, changePct, windowDays, paperCount, note}`；`trend` 为 `up` / `down` / `flat` | `MAP_SECS.热点变化` |
| `benchmarksAndBaselines[]` | 数组 | `{name, kind, usedByCount, note}`；`kind` 为 `benchmark` / `baseline` | `MAP_SECS.评测与基线` |
| `gaps[]` | 数组 | `{title, kind, metric, note, sources}`；`kind` 为 `gap` / `finding` | `MAP_SECS.空白与其它发现` |
| `categories[]` | 数组 | `{routeKey, name, paperCount, note}`；`routeKey` 与 `classics.routes[].key` 共用 | `MAP_SECS.分类` |
| `hotspots` | 对象，可选 | `{source, months[], totals[], items: [{name, summary, terms[], counts[], onset, peak, recentSharePct, examples}]}`：`counts[i]` 是 `months[i]` 这个月命中该热点的论文数，`totals[i]` 是当月论文总数；`items` 按 `onset` 排序 | 新增（“热点演变”） |

### 5.16 `llm-settings`（大模型引擎）

后端需要大模型的地方（目前是“重新整理关键词”）都走同一个可切换的引擎。

| `key` | 引擎 | 怎么配置 |
|---|---|---|
| `claude-code` | 本机 Claude Code 命令行（`claude -p`），用你已登录的账号 | 装好 Claude Code 即可；不在 PATH 上时用环境变量 `PWB_CLAUDE_BIN` 指定路径 |

`llm-settings`：`{engine, updatedAt, engines: [{key, name, ready, detail, model, defaultModel}]}`。`ready` 表示这个引擎现在能不能用，`detail` 是命令路径或缺什么。

## 6. 任务（按钮 → 后端执行）

面板上原来只写本地日志的按钮（`stub()`），都改为 `POST /tasks`：

```json
{ "type": "deep-read", "params": { "paperId": "arxiv-2610.32060" } }
```

请求头带 `Idempotency-Key: <前端生成的随机串>`，后端对同一个 key 只建一个任务，重复提交时返回同一个任务。

后端立即返回 `202` 和 `task`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | 字符串 | 形如 `task-20261027T153000-a1b2c3` |
| `type` / `params` | | 同请求 |
| `status` | 枚举 | `queued` / `running` / `done` / `failed` |
| `createdAt` / `updatedAt` | 时间 | |
| `progress` | 对象 / null | `{done, total, message}` |
| `message` | 字符串 | |
| `outputs[]` | 数组 | `{kind, path}`；`path` 为可以 GET 的接口路径，例如 `/papers/arxiv-2610.32060/deep-read` |
| `error` | 字符串 / null | |

前端每隔几秒查一次 `GET /tasks/{id}`，直到 `done` 或 `failed`。参数不合法直接返回 400，不建任务。

任务类型：

| `type` | `params` | 对应按钮 | 产物 |
|---|---|---|---|
| `deep-read` | `{paperId}` | 论文卡片"Codex 精读" | `/papers/{id}/deep-read` |
| `generate-report` | `{type, period}` | 报告页"生成本周周报" | `/reports/{id}` |
